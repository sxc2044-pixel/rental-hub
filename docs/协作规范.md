# 协作与需求变更规范

正式项目采用main作为可交付主分支，feature分支承载单项变更。课程中的master、dev、feature练习在独立本地仓库执行，见evidence中的bundle与日志，不与正式业务代码的历史混用。

每次提交围绕一个明确变化，使用feat、fix、test、docs、chore前缀。不提交数据库口令、恢复密钥、运行数据、上传材料、临时日志、Maven仓库或开发工具。提交前至少运行与修改相关的测试；影响鉴权、状态机、SQL或事务时执行完整verify。

审查要点为角色与数据归属、输入范围、参数绑定、事务边界、状态转换、敏感字段和失败返回。变更FR时同步需求跟踪、接口、设计图和测试。审查中的拒绝理由应能定位具体触发条件与实际影响。

需求变更记录应包括原编号、变化、原因、受影响模块与表、兼容性、验证方法及确认状态。未取得确认的业务选择按本期实现约定记录，不改写成需求方已批准的结论。公开发布、创建GitHub仓库或向他人发送消息不作为本地实验的默认操作。
